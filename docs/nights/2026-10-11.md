## Исправления

### 1. Task board терял пустые строки в тексте карточки (`realm/tasklist.py`) — 8d05c213

**Что было.** mail-to-todos: 0 из 3, каждый прогон срезан по таймауту 20 минут (+10247 % времени). Названия всех трёх
писем модель дала за ~36 с, а дальше стенд ждал.

**Причина.** Пустая строка внутри текста карточки записывалась в `TASKS.md` пустой строкой файла, а при чтении
пустые строки пропускались. Когда добавлялась следующая карточка, доска перезаписывала файл уже без абзацев —
письмо «From / Subject / пустая строка / текст» теряло пустую строку. Стенд ищет карточку по точному тексту и не
находил её. Это и настоящая потеря данных у человека: абзацы в карточках исчезали при каждой следующей записи.

**Что изменил.** Чтение: пустые строки внутри карточки остаются в её тексте, если за ними идёт продолжение этой же
карточки. Тест `test_a_cards_empty_lines_survive_the_next_card` (без исправления падает).

**Цифры** (`check --scenario todos`): mail-to-todos 0/3 → 3/3; время +10247 % → +9 %; токены +222 % → +107 %.

### 2. Task board называл каждую карточку отдельным вызовом (`core/workers/fields.py`, `realm/tasklist.py`) — 7a7d6e62

**Что было.** long-cards: +2900 % токенов. Четыре длинные карточки → четыре вызова модели, запущенные одновременно,
поэтому почти все «холодные»: у agy ~22 тыс. токенов системного промпта на вызов без кэша. Голый инструмент
называет все четыре одним вызовом.

**Что изменил.** Карточки, пришедшие в пределах 0,3 с друг от друга (до 10), называются одним вызовом — по
пронумерованному названию на карточку; если ответ пропустил карточку, её название — первые слова, как и раньше.
Одна карточка спрашивается прежним промптом. Тесты: разбор пакетного ответа и «две карточки — один вызов» в
`test_bench_kits.py`.

**Цифры** (`check --scenario todos`): long-cards токены +1377 % → −9 % (в полной проверке до этого было +2900 %),
время +37 % → +22 %; mail-to-todos токены +107 % → −91 %. Качество 3/3 везде; названия хорошие, русская карточка
названа по-русски. boiler-with-contacts (там нет названий, код не задет) по времени +27 % → +87 %: его единственный
вызов плана шёл 13–19 с вместо ~12 с — рядом шла перепроверка картинок на том же аккаунте agy.

### 3. Review board: члены совета отвечали по очереди (`realm/team.py`, `core/workers/council.py`) — 266af08d

**Что было.** planted-flaws +216 % времени, route-a-request +253 %. Ревью членов независимы (никто не читает чужое
ревью), но спрашивались одно за другим.

**Что изменил.** Настоящий совет спрашивает членов одновременно (`team.run(together=True)`), если ни у кого из них

«Продолжить» спросит только его. Тесты и песочница сохраняют старый порядок. Метка расходов передаётся в потоки.

**Цифры** (`check --scenario board`, медианы здания): planted-flaws 40,7 → 37,4 с (+216 % → +190 %), токены
48,1k → 8,5k; route-a-request 34,6 → 26,3 с (+253 % → +168 %), токены 46,9k → 52,7k. Качество 3/3. Токены на agy
скачут из-за кэша; вызовы, запущенные разом, и холодными стартуют вместе — за этим стоит последить.

## Что не получилось и почему

- **customer-orders: +750 % токенов — это не здание, а порядок вызовов и кэш agy.** Здание — первый вызов всей
  проверки, кэш «холодный» (~22,4 тыс. входных токенов); голый инструмент идёт сразу за ним, кэш «тёплый» (~2,4 тыс.
  + 19,7 тыс. из кэша), и его ответ потом читается из сохранённого. В on-call, где кэш тёплый у обоих, токены здания
  всего на +9 %. Проверил отдельно: два одинаковых вызова agy подряд — первый 21,9k, второй 2,0k + 19,8k из кэша,
  во временных папках так же. Чтобы это исправить, надо менять саму проверку (как считать токены из кэша или в
  каком порядке звать стороны), а это я по правилам ночи не трогал.
- **Review board всё ещё дорогой** (+168…+190 % времени): совет — это 2 ревью + решение распорядителя, минимум два
  последовательных вызова против одного у голого инструмента. Бюджет +50 % для него недостижим без смены самой
  идеи (например, пропускать распорядителя, когда все одобрили и выход один).
- **Картинки рисуются ~20 минут** на gemini-flash-low: agy правит пиксели скриптами. Работает, но медленно.
- `tests/test_updates.py::test_homebrew_upgrades_with_brew_and_restarts_under_opt` падает и на чистом `main` — на
  этой машине установлен Homebrew, тест это не изолирует. Не связано с ночными правками.
- Около 7 часов ночи пропало: между шагами машина, похоже, засыпала (проверка закончилась в 22:00, следующий шаг —
